## 平台行为与实现调整

1. `install_init` 发生在应用解包及 Compose 解析之前。必须预先生成 `etc/current/server.env`；否则应用中心报 10266。root 仅准备本应用目录，配置生成随即降为包用户；runtime 的 bootstrap 副本随 FPK 打包，不依赖尚未解包的 app 内容。
2. 平台解包后重新设置目录属主。生命周期在本应用私密 etc 树中用目录描述符和不跟随链接的文件打开方式恢复属主，随后降权。包用户没有 Docker 组权限。
3. 宿主 `www-data` 的实际 GID 必须动态读取；本机实测为 712，不能套用 Debian 常见的 33。包用户实际主组为 AppUsers，Socket 探测须保留该组并加入网关组。
4. 网关只读挂载应用代码，另将 `target/run` 挂载为可写 Socket 目录；飞牛入口通过 `target/woodpecker.sock -> run/woodpecker.sock` 连接。Socket 目标权限 0660，目录 0750，仅 root 和宿主网关组可访问。
5. **应用中心普通启动复用已有容器。** 即使 Compose 中配置代次 label 已改变，实测容器 ID 未改变，旧容器仍保留旧挂载。配置向导已阻止修改并保留旧配置；label 仅作为未来真实重建时的标识，不能作为已生效证明。
6. **`install-fpk` 对已安装应用直接返回，未执行升级。** 递增版本也未触发升级。`install-local` 实测尝试卸载重装，卸载脚本错误后仍报告成功并清理应用目录，但遗留运行容器。它不能作为可靠的升级或数据保留通道。
7. 清理由上一步留下的测试容器时，仅按 `com.docker.compose.project=woodpecker` 筛选并停止/删除本次测试项目；未执行全局 prune，也未改动其他应用。
8. 升级/卸载脚本的维护许可只能保护遵守回调结果的平台流程。上述 CLI 行为说明它不能成为唯一的数据保护措施；必须独立保存并验证外部冷备。
